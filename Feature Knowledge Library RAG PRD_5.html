【Feature Platform】Feature Knowledge Library RAG PRD

Summary

收到 4 个需求：1. 将现有 Feature List 升级为可检索的 Feature Knowledge Library；2. 在特征详情页展示可向量化的结构化文本与 RAG 状态；3. 在新建特征流程中提供 New feature entry · Ask AI，让有 RAG 编辑权限的用户通过 Agent 问答生成新 feature 方案；4. 提供常驻 Ask AI 入口，帮助业务方用自然语言发现特征并跳转详情。

We have received 4 requests: 1. Upgrade the existing Feature List into a searchable Feature Knowledge Library; 2. Show embedding-ready structured text and RAG status on the feature detail page; 3. Provide New feature entry · Ask AI in the new feature flow, so users with RAG edit permission can generate a new feature proposal through Agent Q&A; 4. Provide an always-on Ask AI entry for feature discovery and detail navigation.

Background // 需求背景

What are we building? // 需求概述

  1. Problem 1: Feature Platform 当前已有大量特征，但业务方通常只熟悉自己提过的几十个特征，找特征仍依赖人工问平台同学；特征含义、代码逻辑、适用范围、稳定性与数据源信息缺少一个可被 RAG 检索的统一知识层。

    Problem 1: Feature Platform has thousands of features, but business users usually only know the small subset they previously requested. Feature discovery still relies on asking platform owners manually, and feature semantics, code logic, usage scope, stability, and data source details are not organized as a unified RAG-searchable knowledge layer.

  2. Problem 2: 现有 Feature List 更像资产列表，缺少 embedding 状态、同步状态、失败重跑与可召回性验证，无法让 PM/RD 判断某条特征是否已经进入 Ask AI 可用范围。

    Problem 2: The current Feature List works as an asset inventory, but it does not expose embedding status, sync status, failed re-index handling, or recall validation. PM/RD cannot easily tell whether a feature is ready for Ask AI.

  3. Problem 3: 新建特征时，用户不应该先手填一堆 RAG 字段；更自然的路径是先从业务诉求描述开始，由 Agent 追问 feature meaning、entity、data source、owner、usage example、risk / limitation，并生成新 feature 方案供确认。

    Problem 3: In the new feature flow, users should not start by manually filling a long RAG template. The better path starts from describing the business need, then lets the Agent ask for feature meaning, entity, data source, owner, usage example, and risk / limitation, and generate a new feature proposal for confirmation.

  4. Problem 4: 业务方需要在平台内直接用自然语言问“我该用哪个特征 / 逻辑是什么 / 稳定性如何”，并从结果卡片跳回特征详情页完成确认。

    Problem 4: Business users need an in-platform natural-language entry to ask which feature to use, how a feature works, and how stable it is, then navigate from result cards back to feature details for confirmation.

User Story Route

  1. PM/RD 进入 Feature Platform → 特征 Agent 应用 → Knowledge Library，查看 indexed/failed 总量，通过 Feature name/code、Feature type、Owner entity、Data Source Extra、RAG Status 筛选特征。PM/RD enters Feature Platform → Feature Agent app → Knowledge Library, checks indexed/failed totals, and filters features by name/code, type, owner entity, data source extra, and RAG Status.
  2. 用户点击 View RAG 进入特征详情页，检查 Meta、Structured Text 与 embedding 状态；F2 不承载新 feature 创建或补录任务，只用于查看和最终确认。The user clicks View RAG to open the feature detail page and checks Meta, Structured Text, and embedding status. F2 does not host new-feature creation or backfill tasks; it is for viewing and final confirmation only.
  3. 有 RAG 编辑权限的用户进入 F3 新建特征页，先看到 New feature entry · Ask AI 空态入口：Start Agent Entry 按钮在 Start from describing 之前，提示用户从描述业务诉求开始，而不是手填模板。A user with RAG edit permission enters the F3 new feature page and first sees the empty-state New feature entry · Ask AI entry. The Start Agent Entry button appears before Start from describing, guiding the user to start from the business need instead of manually filling a template.
  4. 用户点击 Start Agent Entry 后打开 Agent Entry 窗口；左侧 Agent Q&A 收集字段，右侧实时渲染 Generated New Feature Proposal，并用 Required N/19 展示必填完成度。After clicking Start Agent Entry, the Agent Entry window opens. Agent Q&A on the left collects fields, while the right side renders the Generated New Feature Proposal and shows required-field completion as Required N/19.
  5. 达到 19/19 后用户点击 Confirm Proposal 锁定方案，再运行 6 项 Skills Evaluation；如果返回 EVALUATION_FAILED，用户按建议回到 Q&A 补充，更新后的 Proposal 必须重新 Confirm / Evaluate。At 19/19, the user clicks Confirm Proposal to lock the proposal and runs six Skills Evaluation checks. If EVALUATION_FAILED is returned, the user adds the requested information through Q&A, and the updated proposal must be confirmed and evaluated again.
  6. 只有最新 Proposal 达到 Evaluation 6/6 才启用 Submit。Submit 后写入 Feature Platform Meta + Knowledge Library 并进入 embedding queue；embedding 成功后进入 INDEXED。提交后当前 conversation 关闭，下一条 feature 必须新开 conversation。Submit is enabled only when the latest proposal passes Evaluation at 6/6. After Submit, write to Feature Platform Meta + Knowledge Library and enter the embedding queue; the feature becomes INDEXED after embedding succeeds. The current conversation closes after submission, and the next feature requires a new conversation.
  7. 业务方在任意页面点击 Ask AI；系统按 NEED_CLARIFICATION / FEATURE_CARDS / LOW_CONFIDENCE / NO_RESULT 返回对应状态。正常 Feature Card 可跳 F2；无结果创建分支按 RAG 编辑权限进入 F3 或申请权限 modal。Business users can click Ask AI from any page. The system returns NEED_CLARIFICATION / FEATURE_CARDS / LOW_CONFIDENCE / NO_RESULT as applicable. Normal Feature Cards open F2; the no-result creation branch opens F3 for users with RAG edit permission or an apply-permission modal otherwise.

Structured Text Generation // 结构化文本生成

  1. 系统从 Feature Meta + Knowledge Library Extension 拼装 structured text，字段顺序建议为 FEATURE、TYPE、ENTITY、VALUE、DESCRIPTION、USAGE SCOPE、DATA SOURCE、CODE LOGIC、RATE LIMIT、RISK / LIMITATION；categorization features 额外拼入 OUTPUT SAMPLES（完整 value → meaning），model features 跳过。The system assembles structured text from Feature Meta + Knowledge Library Extension. Recommended order: FEATURE, TYPE, ENTITY, VALUE, DESCRIPTION, USAGE SCOPE, DATA SOURCE, CODE LOGIC, RATE LIMIT, and RISK / LIMITATION. Categorization features additionally include OUTPUT SAMPLES (complete value → meaning); model features skip it.
  2. Regenerate 只重新生成 structured text，不直接覆盖用户原始填写字段；用户确认后才触发重新 embedding。Regenerate only rebuilds structured text and does not directly overwrite user-entered source fields. Re-embedding is triggered only after user confirmation.
  3. 每次成功 embedding 后更新 vector_id、chunk_count、last_synced_at 与 rag_status。After each successful embedding run, update vector_id, chunk_count, last_synced_at, and rag_status.

Permission & Agent Evaluation // 权限与 Agent 评估

  • Feature Discovery 读能力面向所有可访问 Ask AI 的用户；新 feature 创建写能力仅面向有 RAG 编辑权限的用户。Feature Discovery read capability is available to all users who can access Ask AI. New feature creation write capability is only available to users with RAG edit permission.
  • Agent 路径与手动模板共用 19 个必填字段和同一 Evaluation gate；未达到 19/19 不允许 Confirm / 进入 Evaluation，手动模板不得绕过。The Agent and manual-template paths share the same 19 required fields and Evaluation gate. Before 19/19, Confirm / Evaluation are blocked, and the manual path cannot bypass the gate.
  • Confirm 只锁定当前 Proposal version，不写入正式库。任何 Q&A 修改都会产生新 version，并使旧 Confirm 与旧 Evaluation 结果失效。Confirm only locks the current proposal version; it does not write to the production library. Any Q&A edit creates a new version and invalidates the previous Confirm and Evaluation result.
  • Skills Evaluation 固定检查 6 类：必填字段完整度、语义清晰度、source / owner 可追溯、usage example 可召回、risk / limitation 覆盖上线边界、classification / region 一致性。失败必须返回逐项修改建议并支持重新评估。Skills Evaluation checks six categories: required-field completeness, semantic clarity, source / owner traceability, usage-example recallability, risk / limitation coverage of launch boundaries, and classification / region consistency. Failures must return itemized fixes and support re-evaluation.
  • Evaluation 6/6 只启用 Submit。用户 Submit 后才写入 Feature Platform Meta + Knowledge Library 并进入 embedding queue；embedding 成功后 INDEXED 生效并可被 Ask AI 召回。A 6/6 Evaluation only enables Submit. Feature Platform Meta + Knowledge Library are written and the embedding queue starts only after the user submits. INDEXED becomes effective and retrievable by Ask AI after embedding succeeds.
  • 批量 Re-index 需要记录操作者、时间、特征数量、成功/失败数量与失败原因。Batch Re-index must log operator, time, feature count, success/failure count, and failure reasons.
